# Security audit, 2026-10-14

Audited commit: `9858229` (`main`). Method: manual source review of contracts, mock-bank/chain code and web API, plus the
60-test contract baseline. No exploit code was written; evidence marked `[code-read]` was read, `[tested]` is covered by
an existing test. Base Sepolia demo only: nothing here proves exploitability against a live deployment.

## Design principle (owner decision, 2026-10-14)

The system follows the P2P-exchange model: funds stay locked in escrow until the counterparties explicitly confirm the
deal, with a neutral arbiter only for disputes. Findings are judged against that: a payment must not be released
by anything other than an explicit confirmation (AW-H-02), and the neutral arbiter must stay neutral for the whole
life of a deal (AW-M-03).

## Executive result

No Critical issue was identified. I found two High, three Medium, and one Low issue. The most urgent issue is a production-path concurrency error that can attach two users to the same wallet while orphaning the wallet actually deployed by the second transaction. The other High issue is that adversarial evidence reaches the LLM and can trigger an autonomous, capped release without a deterministic acceptance or injection gate.

The unchanged contract baseline passes all 60 legitimate tests. No PoC or exploit test was written or run. Findings not exercised by that existing suite are marked `[code-read]`.

### Severity notes

- AW-H-01 crosses the application's tenant boundary and can grant one customer control of another customer's wallet through normal API calls.
- AW-H-02 is capped by the session policy, so it is not Critical, but it defeats the core “verify evidence before autonomous payment” promise.
- AW-L-01 is dormant because there is no production caller for `fundJustInTime`; promote its priority before exposing that flow.

## High-severity evidence chains (no exploit code)

### AW-H-01 — stale factory return crosses wallet ownership links

Exact chain: `send` performs `simulateContract` before calling `serialize` (`web/src/lib/chain.ts:154-166`); only the actual `writeContract` is queued (`:166-173`). `createWorkspace` trusts `outcome.result` as the new address (`web/src/lib/actions.ts:37-60`) and immediately uses it for `setFileEscrow` (`:61-69`). The POST route then persists that address in `UserWallet` and attaches a bank account (`web/src/app/api/workspace/route.ts:23-26`). Factory creation is nonce/order-dependent and emits the authoritative address (`contracts/contracts/AgentWalletFactory.sol:18-22`). Two simulations against the same pre-state therefore return the same first address, while the sequential transactions consume different factory nonces and deploy different contracts. `[code-read]`

Preconditions: two workspace requests overlap before the first create is mined; both are authenticated and pass `freeLinkedAccount`; the same factory and owner role are used. The second request receives wallet A, configures A, links A to its own user, and may attach its account to A, while transaction two deployed B. Since every demo wallet has the shared server owner key, `userWallet` then permits customer 2's owner-signed actions against A.

Owner regression/invariant test: write a web integration test with a controllable public client barrier so both simulations complete before either write proceeds. Use two users and two free accounts. After both calls resolve, decode `WalletCreated` from each receipt and assert (1) response address equals its own receipt event, (2) addresses differ, (3) each address has exactly its intended user link and backing account, and (4) FileEscrow was configured on both deployed wallets. This test should fail under the current pre-queue simulation design and pass when receipts are authoritative.

### AW-H-02 — adversarial evidence can become an autonomous payment instruction

Exact chain: contractor evidence is stored as text in a data URI (`web/src/lib/actions.ts:222-231`; `contracts/contracts/MilestoneEscrow.sol:118-128`). `dealsSummary` copies up to 4,000 characters into `text_untrusted` for the LLM (`web/src/lib/agent.ts:204-227`). The upload pre-scan is explicitly advisory and the route calls `runAgent` regardless (`web/src/app/api/workspace/[address]/agent/route.ts:47-51`); evidence later fetched through `list_deals` is not scanned there. Model tool calls execute sequentially (`web/src/lib/agent.ts:416-438`), and `release_milestone` dispatches directly (`:295-298`). The deterministic policy checks state/status/allowlist/caps, but not acceptance criteria, document flags, or justification truth (`web/src/lib/policy.ts:48-70`); an eligible decision sends the direct agent call (`web/src/lib/actions.ts:116-148`). On-chain checks enforce wallet payer/token/payee/caps, not evidence semantics (`contracts/contracts/AgentWallet.sol:276-286,462-480`). `[code-read]`

Preconditions: an allowlisted contractor controls the evidence content; the deal is funded; the milestone status is `EvidenceSubmitted`; its value fits remaining session caps; and the selected model obeys the malicious content despite the system prompt and `text_untrusted` label. The contractor gains the milestone amount. The exploit is nondeterministic across models, but no deterministic control prevents it.

Owner regression/invariant test: mock the model so that, after `list_deals` returns a malicious evidence canary, it requests `release_milestone`. Assert the action executor refuses autonomous execution and produces either `block` or `propose`, with no `agentReleaseMilestone` write. Repeat with benign evidence that lacks a structured acceptance attestation and expect the same result; then supply the separate verifier/human approval artifact and assert only that case may execute. The invariant is “untrusted content alone can never transition a payment from pending to autonomous release.”

## Known items revalidated but not re-issued as new findings

- `_spend` is called only by the three direct agent paths (`AgentWallet.sol:269-299,462-470`). Threshold-approved proposals, owner mandates, arbiter settlement, and owner `execute` do not use session caps. This is reflected in claim (b), not presented as a newly discovered issue.
- `FileEscrow.refund` accepts `Disputed` because it rejects only `Released`/`Refunded` (`FileEscrow.sol:227-233`). It can only return money to the buyer, so I did not inflate it into a loss finding.
- `fundJustInTime` has no production caller; only `web/scripts/funding-check.mts` references it. No settlement/reconciliation daemon was found.
- The authenticated action route exposes caller-selected pause role and `raw_attack`; the latter force-sends a reverting transaction with the shared agent key (`action/route.ts:18-33,43-63`; `actions.ts:235-251`). Combined with the in-process, forwarded-IP rate limit (`guard.ts:69-79`), it can burn shared testnet gas. These were already known and should be removed or demo-gated before public exposure.
- MockTHB pause intentionally blocks mint/redeem but not ERC-20 transfers (`MockTHB.sol:108-119`), allowing already-funded escrows to settle.

### Mandate-specific conclusion

The EIP-712 construction is sound for the reviewed threats: domain includes name/version/current `chainId`/wallet address; the struct hashes all execution fields including dynamic `data`; replay is digest-based; deadline is enforced; and validation uses the current owner (`AgentWallet.sol:350-396`). The existing suite confirms alteration, forgery, replay, expiry, pause, allowlist enforcement, revocation, and invalidation after ownership transfer (`AgentWallet.ts:737-839`). An old signature would become valid again only if the same signer later becomes current owner again before its deadline; short deadlines/revocation remain the operational mitigation. `[tested]`

## Open questions

1. Should an evidence-bearing release ever be autonomous, or should all evidence-based payments require a human/independent verifier regardless of amount?
2. Is the intended production model user-held owner keys and independent approvers, or will the server continue to sign owner actions? The security claims differ materially.
3. Must active escrows block wallet role/ownership changes that create conflicts, or is explicit counterparty-approved arbiter rotation acceptable?
4. What fields may legally be public on Base Sepolia, and should existing demo transactions containing PO/evidence text be disclosed as irreversible testnet data?
5. Before enabling JIT funding, who owns reconciliation, retry scheduling, alerting, and consent enforcement?
